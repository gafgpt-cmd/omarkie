# Photo preview measurements

Run `npm run build`, then `node scripts/benchmark-photo-previews.mjs /path/to/camera.jpg` on the installed shared Electron runtime. Use a real 27 MP JPEG, including a rotated camera photo. The script compares three runs of Electron `nativeImage.createFromPath().resize().toJPEG()` against the production Chromium worker, then reports cold and warm disk-cache lookup times. It uses an isolated temporary profile and leaves the input untouched. These are backend timings; run `npm run test:perf` for end-to-end first-photo time and `node tests/photo-previews-desktop.mjs` for preview/original integrity.

Core uses Chromium `createImageBitmap(blob, {resizeWidth, resizeQuality: "medium"})` and `OffscreenCanvas` in a short-lived Web Worker, created only for an uncached JPEG. The main process serializes jobs so a document with many visible photos cannot launch many simultaneous decoders. No hidden window or native dependency is needed. Chromium's API requests a resized decode; decoder-level JPEG subsampling is implementation-dependent and must be measured, not assumed. Electron nativeImage is synchronous and its documented lack of EXIF orientation handling makes it unsuitable for camera previews without additional correction.

Expected, not measured here: warm previews should remove full-resolution renderer decode and substantially reduce first-photo time. Cold requests add read/IPC/JPEG-encoding work and may exceed the 150 ms budget; compare the benchmark and first-photo suite before claiming a cold-load win. NativeImage may win raw throughput on some hosts but blocks its calling thread. A medium-quality Chromium resize trades some resampling quality for throughput. Every failure serves the original.

The original remains `src`; Chromium chooses a preview through width-descriptor `srcset` and lazy `sizes="auto"`, using the laid-out image width and device pixel ratio. Buckets are 800/1200/1600/2400 pixels; larger displays cap at 2400. Small JPEGs, animation formats, vectors and transparent images retain the original. Copy and export strip preview candidates. Export resource requests, image dialogs and file operations resolve the original document reference, never a cache path. Print HTML strips candidates and loads originals.

Cache files live under userData/photo-previews, keyed by format version, authorized absolute path, mtime, file size and width. Hits update recency; misses enforce a 128 MiB cap by moving the oldest entries to the OS Trash. The cap describes the active cache; OS Trash retention follows desktop policy. No files are written into document folders. Clearing the cache is safe. A changed source creates a new key, and changes during decoding abort caching.

Optional plugin proposal: sharp/libvips can decode JPEGs with shrink-on-load and generate previews outside the UI process, potentially lowering cold latency and IPC volume. It must remain an optional, explicitly installed plugin with an architecture-specific native binary, never a core runtime dependency. The existing sharp dev dependency is used only for test fixtures and assertions. The benchmark intentionally does not select a core backend from dev-only sharp availability.

API references: [Electron nativeImage](https://www.electronjs.org/docs/latest/api/native-image), [Chromium worker createImageBitmap API](https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope/createImageBitmap).
